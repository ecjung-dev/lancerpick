# 전자계약 버전·서명 기반 1차 구현

작성일: 2026-11-05. 공유 브랜치: feature/advanced-common-foundation. 초기 작업 브랜치 feature/contract-finance-foundation에서 공통 기반을 분리했다. 정책은 [4인 설계](advanced-design-four-person.md)를 따른다.

현재 반영 상태(2026-11-05): 아래 V3/V4 기반은 PR #76으로 main에 반영됐고, main `1e10d78`에는 V5/V6 누적 29개와 [정책 경계 보완](advanced-policy-boundary.md)도 포함된다. 기존 명령의 V2 차단·허용 행동·정책 DTO는 반영 완료이며 신규 계약 주문/API·PDF·분할 결제 연결은 미완료다. 아래 19개 스키마와 결제 외 명령 재검토 필요 문장은 최초 공유 당시 기록이다.

공유 전 최종 검증: 2026-11-05, 격리 MySQL 8.4에서 V1~V4·JPA validate 포함 clean build 전체 **651건 통과, 실패·오류·건너뜀 0**. 아래 최초 실패와 부분 재검증 기록 이후, 수정된 전체 소스를 한 번에 재실행한 결과다. 프런트·브라우저·원격 CI 결과와 구분한다.

## 구현

- V4__add_order_contracts.sql: order_contracts·contract_signatures 두 테이블. 주문당 현재 계약 한 개·버전 중복·역할별 서명 중복·서명 파일 필수값을 DB에서 제한한다.
- contract/entity·repository·service·dto: 계약과 서명 JPA 매핑, 판매자의 특약 초안 생성·교체, 양측 해시 확인 후 서명, 양측 완료 시 SIGNED.
- 표준 본문은 contracts/standard-v1.txt의 고정 양식이다. 상품의 현재 정보 대신 주문 스냅샷·가격·소요일과 양측 표시 이름을 문서에 고정한다. 특약은 5,000자 이내다.
- 서비스 잠금은 회원 공유 잠금 → 주문 쓰기 잠금이다. READ_COMMITTED에서 현재 버전을 확인하고 이전 계약을 SUPERSEDED로 전환·flush한 뒤 새 버전을 추가한다.
- 이전 서명은 보존하지만 새 버전에 재사용하지 않는다. SIGNED 내용은 교체할 수 없다. 동일 초안 재요청과 동일 당사자의 서명 재전송은 추가 행을 만들지 않는다.
- 문서 JSON은 현재 필드가 모두 스칼라인 고정 스키마이며 키 정렬 후 SHA-256을 계산한다. MySQL JSON 재조회 시 키 순서가 바뀔 수 있어 같은 정렬 규칙으로 복원·검증한다. 표준 본문의 줄바꿈도 LF로 정규화한다. PDF 해시는 별도로 보관한다.
- 기존 전액 결제 API는 CONTRACT_V2 주문을 CONTRACT_PAYMENT_NOT_READY로 차단한다. 계약 주문이 서명 없이 기존 API에서 전액 차감되지 않도록 한 안전장치다.

## 단계별 연결 한계

기존 주문 생성 API는 아직 LEGACY_V1만 생성한다. 계약 서비스는 내부 명령이며 HTTP Controller·React 계약 화면은 추가하지 않았다. 새 계약 주문 API·AWAITING_CONTRACT 상태 연결·계약 이력 이벤트는 다음 단계다.

현재 서비스는 CONTRACT_V2·판매자 수락 완료·미결제·AWAITING_PAYMENT·대기 취소 요청 없음만 처리한다. 이는 신규 주문 활성화 전의 내부 기반이다. 신규 API를 열 때 계약 대기 상태와 양측 서명 후 선금 대기 전환을 함께 구현해야 한다.

PDF 렌더러·비공개 저장·당사자 다운로드는 아직 연결하지 않았다. completeGeneration은 내부 렌더러 결과 반영용 엔티티 메서드이며 클라이언트가 파일 키·해시를 제출하는 API를 만들지 않았다. 실제 파일과 메타데이터의 검증·지연 완료 반영·생성 실패 재시도는 렌더러 조율 서비스에서 구현해야 한다.

서명은 인증된 주문 당사자의 문서 확인 이력을 기록하는 모델이다. 외부 서명 서비스·실명 인증·서명 이미지 업로드가 구현된 것은 아니다. 서비스 입력의 memberId는 이후 Controller에서 CurrentMemberId.require()로만 공급한다.

## 검증 범위

기본 통합 검사 7건은 격리 MySQL에서 통과했다. 특약 버전 교체·예전 서명 보존/사용 차단·타인/구매자 초안 권한·중복 서명·양측 완료·파일 해시 불일치·늦은 렌더러 결과 차단·기존 결제 우회를 포함한다. 렌더러 결과는 테스트 fixture이며 실제 PDF 파일을 생성한 검사는 아니다.

최종 검사에는 별도 스레드·실제 커밋으로 같은 초안 동시 생성과 양측/중복 동시 서명을 추가했다. 전체 651건 실행에서 계약 9건을 포함한 643건은 통과했고 DB 없는 DefaultCatalogApiTests 8건은 새 서비스의 대체 객체 누락으로 실패했다. 해당 클래스에만 MockitoBean을 추가한 뒤 이 8건을 재실행해 실패·오류·건너뜀 0으로 통과했다. 수정 후 전체 651건을 한 번에 다시 실행한 결과와는 구분한다. 운영 소스는 재검증 때 변경하지 않았다. 이전 금융 기반 642건과 단순 합산해 최신 실행 수로 표현하지 않는다.

최초 계약 검사에서는 JUnit Order와 엔티티 Order의 와일드카드 import 충돌을 수정했다. 현재 테스트는 명시적 JUnit import를 사용하며 컴파일 실패를 테스트 통과로 계산하지 않는다.

신규 주문 API 활성화 전에는 기존 취소·납품·확정 API도 정책별 허용 행동을 재검토해야 한다. 현재 결제 API 차단만으로 전체 CONTRACT_V2 업무 흐름의 검증이 끝났다고 판단하지 않는다.

## 마이그레이션

실행 스키마는 V1/V2 17개 + V3 컬럼 확장 + V4 계약 2개로 업무 테이블 19개다. 목표 신규 12개 중 2개가 추가됐다. 각자의 DB에 다음 서버 시작 시 V3/V4가 적용될 수 있으므로 기능 브랜치의 코드와 migration을 함께 사용한다. 이번 직접 검증은 격리 DB만 사용한다.

전체 DDL 후보는 V1/V2 기준 검토본이며 V3/V4 적용 DB에 그대로 실행하지 않는다. 다음 마이그레이션은 현재 V4를 기준으로 차분 작성한다. 이미 적용한 V1/V2/V3는 수정하지 않는다.
