# 주문별 실시간 채팅·세션 폐기

후속 화면/회원 정책(2026-11-09, 미구현): [개편 문서](ui-renewal-member-policy.md) §4·§11에 헤더 대화 목록과 그 왼쪽 별도 채팅창을 정리했다. 현재 주문별 메시지·세션·복구 경계를 재사용하며 대화 목록/읽음 API 지원은 후속 확인 사항이다. 일반 제한의 기존 거래 채팅은 허용하고 보안 잠금은 연결/전송을 차단한다. 운영 문의 채팅과 합치지 않는다. 이번 문서화로 소켓/API를 변경하지 않는다.

2026-11-05 구현, 2026-11-06 통합 정리. 작업 브랜치 `feature/order-chat-realtime`에서 저장형 채팅 커밋 `8e92e28` 위에 WebSocket/STOMP를 연결한다. 금융 기능이 반영된 main `03b5687`에서 시작해 검색·자동 구매 확정 타이머·판매자 공개 소개와 문서 변경(main `5a36ef4`, #96~#101)을 통합했다. 채팅의 main 병합·원격 CI 통과 완료를 뜻하지 않는다. [저장형 API·정책](order-chat-storage.md)을 그대로 재사용한다. 새 테이블·Flyway 변경은 없다.

## 제공 범위와 담당

- J1: 주문 상세의 실시간 전송/수신, 재연결, 순번 기반 누락 복구. 전송 실패 시 같은 UUID로 사용자가 재확인/재전송한다.
- C2: HTTP 세션·회원 인증 버전 검사, 계정 전환·로그아웃·비밀번호 변경/재설정에 따른 소켓 종료. 기존 `AuthVersionLookup` 계약을 사용하며 회원 기능 정책을 바꾸지 않는다.
- 구매자·판매자만 해당 주문의 메시지를 작성/조회한다. 종료 주문은 조회 전용이고 기존 키의 재확인은 중복 저장하지 않는다. 관리자 권한도 타인의 대화 전문 열람을 허용하지 않는다.
- 읽음 표시·파일 첨부·편집/삭제·미접속 메시지 알림·관리자 상담·Redis Pub/Sub는 이 구현에 포함하지 않는다.

## 연결 계약

| 구분 | 경로·데이터 | 검사·결과 |
| --- | --- | --- |
| WebSocket handshake | 같은 출처 `/ws` | 기존 HTTP 로그인 세션 필요. Origin 기본 동일 출처 검사. SockJS·쿠키/토큰 URL 전달 없음 |
| STOMP CONNECT | 새 `GET /api/auth/csrf`의 `headerName: token`, `X-Chat-Member-Id: 현재 회원 ID` | Spring `XorCsrfChannelInterceptor`로 마스킹 CSRF 검증. 회원 ID 헤더는 계정 전환 경쟁 검출용이며 인증 주체는 서버 세션 |
| SUBSCRIBE | `/user/queue/chat`, `/user/queue/chat-errors` | 연결별로 두 종류만, 중복/임의 destination 거부. 회원 ID를 넣는 공개 topic은 제공하지 않음 |
| SEND | `/app/orders/{orderId}/chat/messages` | JSON `{clientMessageId, content}`. 발신자는 서버 연결에서 결정. HTTP와 같은 저장 서비스의 권한·상태·멱등 검증 |
| 저장 메시지/재확인 응답 | `/user/queue/chat` | 기존 `ChatMessage` JSON. 문자열 BIGINT ID/순번. 새 메시지는 커밋 이후 양측 회원의 유효한 연결에 전달. 동일 키 재확인은 요청 연결에 응답 |
| 업무 오류 | `/user/queue/chat-errors` | `{orderId, clientMessageId, status, code, message, fieldErrors, traceId}`(C1, [공통 계약](event-contract.md#4-채팅-소켓-오류-형식)). `CHAT_CLOSED`, `RESOURCE_NOT_FOUND`, `IDEMPOTENCY_KEY_REUSED` 등 저장 서비스 오류는 그 HTTP 상태, 형식 오류는 400 `INVALID_REQUEST`, 예상치 못한 실패는 503 `CHAT_SEND_FAILED`로 원문 숨김 |

구독·전송은 승인 목록 외 기본 거부한다. STOMP의 login/passcode나 클라이언트 senderId로 인증하지 않는다. 서버 연결별 임의 라우팅 ID를 사용하고 HTTP 세션 ID를 메시지/클라이언트에 노출하지 않는다.

인증 실패는 WebSocket close `4401`, CSRF·허용되지 않은 구독/프레임은 `4403`, 연결/전송 제한은 `4429`다. 안전한 고정 코드만 close reason에 포함한다. 구문 파싱 오류는 안전한 STOMP ERROR 후 종료할 수 있다. 클라이언트는 인증/권한 거부 후 무한 재접속하지 않고 대화를 숨겨 재확인을 요구한다. 용량 제한 후에는 수동 재연결을 제공한다.

Spring의 순서 보존 채널은 인터셉터 예외를 내부에서 처리할 수 있다. 따라서 `ChatInboundSecurity`가 CSRF/권한 거부를 잡아 **연결을 직접 종료하고 프레임을 폐기**한다. 예외만 던지고 연결이 닫혔다고 가정하지 않는다.

## 저장·트랜잭션·전달 경계

1. 회원 공유 잠금 → 주문 쓰기 잠금 → UUID 재확인 → 참여자/상태 검증 → 순번 증가·메시지 저장을 하나의 DB 트랜잭션으로 처리한다.
2. 같은 트랜잭션에 인메모리 `ChatMessageStored` 이벤트를 발행한다. `AFTER_COMMIT` 리스너가 양측의 유효한 소켓에 전달하므로 롤백한 메시지는 전달하지 않는다. 소켓 I/O로 DB 잠금 시간을 늘리지 않는다.
3. 전달 실패는 이미 커밋된 메시지를 취소하지 않는다. 메시지 원문을 아웃박스에 복제하지 않고 저장된 채팅을 순번으로 재조회한다. 이 이벤트는 영속 아웃박스가 아니며 전달 자체를 보장하지 않는다.
4. 재연결 시 개인 큐를 구독한 뒤 `GET .../messages?afterSequence=마지막복구순번&limit=100`을 끝까지 조회한다. 실시간 프레임의 큰 순번만 보고 cursor를 건너뛰지 않는다.
5. 마지막 한 건의 전달 누락과 구독 준비 경쟁도 회복하도록 15초마다 보충 조회한다. 메시지 ID 중복 제거·정확한 BIGINT 순번 정렬을 적용한다. 전송 중 보충 조회에서 같은 UUID가 발견되어도 저장 확인으로 처리한다.

화면은 실시간 연결이 끊겨도 기존 REST 조회/전송을 사용할 수 있다. 소켓 SEND 후 응답이 8초 내 확인되지 않으면 결과 불명확으로 유지한다. 자동으로 다른 UUID를 만들거나 쓰기를 재시도하지 않는다. 재연결은 1~30초 지수 지연·jitter, 연속 실패 최대 8회 후 수동 재연결이다. 소켓 연결마다 현재 회원·새 CSRF를 다시 확인한다.

## 세션·개인정보·자원 한도

- handshake에서 HTTP 세션과 인증 버전을 캡처한다. CONNECT·SEND·SUBSCRIBE 등 수신 프레임과 발송 직전마다 현재 세션 ID/로그인 주체/DB `auth_version`을 다시 검사한다. 세션 ID 회전·다른 계정·세션 무효화·인증 버전 변경은 거부한다.
- 로그아웃 세션 파괴 이벤트로 관련 소켓을 닫는다. 유휴 연결은 기본 5초 주기로 재검사한다. 이미 네트워크로 전달된 프레임을 회수할 수 있다는 뜻은 아니다.
- 소켓 하트비트나 수신 검사는 HTTP 세션의 유휴 시간을 연장하지 않는다. 화면의 정상 HTTP 조회는 기존 서버 세션 정책에 따라 세션 사용에 해당한다.
- 인증 버전 조회 실패도 차단한다. 계정 전환/화면 이탈 시 소켓·재연결/복구 타이머·진행 중 조회를 정리하고 이전 계정 캐시에 늦은 메시지를 넣지 않는다.
- Spring 프로토콜 처리기의 프레임 오류 로그에는 본문·CSRF 헤더가 포함될 수 있어 해당 logger를 OFF로 두고, 전용 보안 처리기에서 고정 오류 코드만 기록한다. 브라우저 STOMP debug 로그도 끈다. 프레임 원문을 찍는 DEBUG/TRACE를 임의로 켜지 않는다.
- 연결은 회원당 8개·서버 전체 256개, 구독은 연결당 2개다. 연결당 10초에 SEND 20개, 순서 보존 큐 진입 전 원시 프레임 60개까지 허용한다. 정상 heartbeat도 원시 프레임에 포함한다.
- 메시지 프레임 한도 16KiB, 송신 버퍼 64KiB, 송신/첫 프레임 대기 10초. 입·출력 실행기는 각각 2개 스레드·큐 100개로 제한한다. 본문은 기존 Unicode 2,000자 제한이다.
- 현재는 **단일 서버의 simple broker**다. 여러 인스턴스로 확장할 때는 세션 공유·Pub/Sub/외부 브로커·폐기 이벤트 전달(C4)을 함께 설계한다. 지금 구현이 다중 서버 전달을 지원하는 것으로 표현하지 않는다. 세션별 DB 인증 검사 비용도 성능 계측 대상이다.

## 로컬 확인

기존 백엔드를 재시작하고 `npm run dev`로 프런트를 실행한다. Vite `/api`와 `/ws`는 같은 `API_PROXY_TARGET`을 사용하며 `/ws`는 Host/Origin을 보존한다. 별도 개인 키나 소켓 서버 실행은 필요 없다. 배포 프록시 설정은 이번 범위가 아니다.

1. 일반 창·시크릿 창에 각 주문의 구매자/판매자로 로그인하고 `/orders/{id}`를 연다.
2. ‘실시간 연결됨’을 확인하고 양측 전송·즉시 수신을 확인한다.
3. 네트워크를 잠시 끊은 동안 상대가 전송한 뒤 복구하면 누락분이 순번대로 나타나는지 확인한다. 동일 메시지를 두 번 표시하지 않아야 한다.
4. 로그아웃·다른 계정 로그인·다른 창에서 비밀번호 변경 시 이전 연결/작성창/캐시가 남지 않는지 확인한다.
5. 종료한 주문은 내역만 유지하고 작성할 수 없는지 확인한다.

## 자동 검증 기록

전체 통합 검증(2026-11-06, main `80840bf` 통합 코드): 격리 MySQL 8.4에서 백엔드 전체 `clean build` **822건 통과(실패·오류·건너뜀 0)**, 프런트 전체 **195건·lint·TypeScript 포함 build 통과**. 검색·자동 구매 확정 타이머와 채팅을 함께 검사했다. 개인 키·개발 DB를 사용하지 않았고 검사 컨테이너는 정리했다. 아래 11/5 기록은 단계별 이력이며 최신 결과와 합산하지 않는다.

추가 main 통합 검증(같은 날, `5a36ef4`, #101): 판매자 공개 소개·판매 상품 조회를 보존하고 작업표 충돌을 해결했다. 프런트 전체 **197건·lint·TypeScript 포함 build 통과**, 변경된 `ProductSearchControllerTests`·`ProductSearchIntegrationTests`는 격리 MySQL에서 **33건 통과(실패·오류·건너뜀 0)**했다. #101 이후 백엔드 전체를 다시 실행한 것은 아니며, 이전 822건과 선택 검사 33건을 합산하지 않는다.

이어서 문서 전용 main `ceec3d8`(#102, 타이머 관리자 해제·관리자 승인 취소 경계)을 통합했다. #101 검증 이후 실행 코드 변경은 없으며, main 반영 완료로 표시된 기능과 문서상 후속 정책은 구분한다.

2026-11-05, 격리 MySQL 8.4의 백엔드 전체 `clean build` **809건 통과(실패·오류·건너뜀 0)**. 개발 DB·개인 키는 사용하지 않았고 검사 컨테이너는 정리했다. 이어 Controller/Service/DTO/config 패키지 분리 후 채팅 **23건을 다시 통과**했다. 전체 809건 재실행과 최종 구조의 표적 재검사를 구분하며 건수를 합산하지 않는다.

마지막으로 응답 직전 세션 폐기 경쟁의 전달 중단을 보완하고, 해당 단위 검사 1건과 최종 `bootJar`를 통과했다. 이 새 1건은 앞선 전체 809건 실행에 포함되지 않는다. 최종 구조는 `chat/controller`·`service`·`dto`·`config`·`event`, 연결 보안은 `chat/realtime`으로 분리한다.

프런트 전체 **188건 통과**, lint·TypeScript 포함 build 통과. 이후 STOMP 클라이언트를 연결할 때만 동적 로딩하도록 분리하고 채팅 16건·lint/build를 다시 통과했다. 기존 500kB 초과 메인 청크 경고는 남아 있다. 새 채팅 클라이언트는 별도 청크로 생성된다.

브라우저 후속 수정: 타이머를 의존성 객체의 메서드로 호출하면서 `this`가 바뀌어 `Illegal invocation`이 발생했다. 기본 `setTimeout`·`clearTimeout`을 `globalThis`에 바인딩했다. 브라우저와 같은 수신 객체 검사를 적용한 회귀 검사는 수정 전 실패·수정 후 통과했고, 프런트 전체 189건·lint/build를 다시 검사했다. 이 검사는 실제 브라우저 수동 확인과 구분한다.

2026-11-06 컨벤션 점검: 공용 연결 상태·오류 응답 타입은 `types.ts`, CONNECT용 새 CSRF HTTP 조회는 `api.ts`, 전송·복구는 `realtime.ts`, Query 캐시 연결은 `useChatRealtime.ts`로 분리했다. 불필요한 non-null 단언을 제거하고, 연결마다 새 CSRF를 조회하는 회귀 검사를 추가했다. main의 주문 상세 타이머와 채팅 패널을 모두 보존했다. 통합 프런트 전체 195건·lint·TypeScript 포함 build 통과. 이전 단계 검사 수와 합산하지 않는다.

- 실제 HTTP 로그인 쿠키·CSRF·네이티브 소켓 7건: REST/소켓 양측 수신·동일 키 재확인, 롤백 미전달·연결 중단 중 저장 후 커서 조회, 익명/다른 출처/잘못된 CSRF/회원 불일치, 임의 구독/브로커 직접 SEND/타인 관리자 거부, 종료 주문 신규 작성 차단·기존 키 응답, 로그아웃 종료, 다른 로그인 세션의 비밀번호 변경 후 종료·다른 회원 연결 유지.
- 세션/프레임 보안 단위 9건: HTTP 유휴 만료·세션 ID 회전·인증 버전 변경·DB 조회 불가 차단, 목적지 기본 거부·구독 한도·SEND 빈도·원시 프레임 빈도·회원 연결 한도·CONNECT 순서. 세션 유휴 만료는 제어 가능한 시계·세션 대역으로 검사한 결과다.
- 기존 저장형 통합 7건도 유지한다. 프런트 실시간 신규 8건은 새 CSRF/회원 헤더·구독, 순번 격차/페이지 복구, 저장 응답 확인, 결과 불명확 시 쓰기 미재시도, 마지막 이벤트 누락의 주기 복구, 계정/세션/CSRF 거부 중단, 해제 후 늦은 응답 차단, 업무 오류/잘못된 프레임을 검사한다.

실제 브라우저 두 계정·Vite 프록시 경유 수동 조작과 원격 CI는 아직이다. 자동 테스트의 실제 소켓 검사와 브라우저 사용자 검증을 혼동하지 않는다.
