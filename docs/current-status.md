# 랜서픽 현재 구현·검증 현황

## 화면 개편·회원 관리 후속 — 문서화, 구현 전

정은찬 제안의 계약/채팅 잠금 공통화(R1, 구현 담당 협의)와 결제/보관 상태 enum 전환(R2, 황준범 담당)도 [개편 문서 §14](ui-renewal-member-policy.md#14-정은찬-제안-리팩토링--구현-전)에 추가했다. 특히 계약 문서의 회원 없음 404와 공통 잠금의 401 차이를 보존 조건으로 기록했다. 구현·DB validate는 수행하지 않았다.

2026-11-09 사용자 합의와 main `5910ccd`(#126)를 기준으로 [개편 문서](ui-renewal-member-policy.md)를 추가했다. 상품 전체 탐색, 헤더 알림/대화 목록과 별도 채팅창, 일반/판매자 탭, 적립금 문구, 구매/판매·수익 조회 조건, 닉네임 6개월 제한·비밀번호 6개월 권고, 황준범 담당 회원 관리/제재를 정리했다. 일반 이용 제한은 신규 활동 차단·기존 거래 허용이며 보안 잠금도 자동 취소/환불하지 않는다. 구매자 보안 잠금은 자동 확정 타이머 시작 차단·중단·관리자 확인 대상이며 자동 재개하지 않는다. 확정 방향과 제안/후속 설계를 구분했다. 이번 변경은 문서만이며 API·DB·화면은 미구현, 문서 PR main 병합 확인 전까지 구현하지 않는다.

## 주문 서비스 구조 정리(동작 변경 없음) — 2026-11-09 로컬

`refactor/order-service-cleanup`, main `de0b72f`(#124)에서 분기. 리팩토링 제안을 Codex로 반박 검토한 뒤 그 조건대로 반영했다. API·DB·Flyway·응답 형식 변경은 없다.

- **정책 판단**: `Order.isFullFunding()`을 추가해 주문 패키지의 `CONTRACT_V3.name().equals(...)` 비교를 바꿨다. 알 수 없는 정책 값 차단은 기존 `TradePolicyVersion.require*`가 계속 맡는다.
- **취소 요청 상태 enum**: `CancellationRequestStatus`(PENDING·APPROVED·REJECTED·WITHDRAWN)와 `@Enumerated(STRING)`+`@JdbcTypeCode(VARCHAR)`(Order.status와 같은 매핑). 저장소 매개변수·Querydsl 조건·JPQL 리터럴·조회 Row·서비스 비교를 함께 바꿨고, 응답 DTO는 문자열 그대로다. 엔티티의 한 줄 압축 코드도 펼쳤다. 계약 서비스 두 곳(`ContractDocumentTransactions`, `OrderContractService`)은 컴파일을 위해 `"PENDING"` 인자만 enum으로 바꿨다(황준범 영역, 동작 동일).
- **UTC 시각**: `common/time/UtcTimes.nowMicros(clock)`. 주문 패키지만 적용했고 시각을 읽는 위치(지갑 잠금 뒤, 자동 확정 재검사)는 그대로다.

## 화면과 동선

- `/`: 실제 `/api/products`·`/api/categories`를 사용한다. DB를 사용하는 기본 실행이 필요하며 demo 예시로 자동 전환하지 않는다.
- `/login`, `/signup`: main에 반영된 로그인·가입 폼. 가입 후 자동 로그인 없이 로그인 화면으로 이동하고, 로그인 후 `?next=` 경로(같은 사이트만)로 돌아간다. 헤더는 `GET /api/me` 결과로 회원 메뉴를 바꾼다. [상세](auth-login.md#프런트-연결-2026-11-04)
- `/products/:id`, `/products/:id/order`: 공개 상품 상세와 요구사항 입력·주문 생성 화면. [상품 상세](product-detail.md)·[주문 진입](order-entry.md)의 구현과 남은 검증 범위를 구분한다.
- `/mypage`, `/mypage/wallet`: 현재 세션을 확인한 뒤 본인 잔액·원장을 조회한다. 구매/판매·정산·판매자 프로필 메뉴를 제공한다.
- `/orders?side=BUYER`, `/orders?side=SELLER`: 마이페이지 메뉴의 목적지다. side·status·page를 URL에 유지하고 잘못된 값은 기본값을 사용한다. 전체 선택에서 status를 생략하고, 구분·상태 변경 시 페이지를 처음으로 되돌린다.
- `/orders/:id`: 결제·직접 취소·확정에 더해 수락·거절·납품·수정·취소 요청과 해결 화면이 연결되었다. 이력·보관 조건·현재 작업 지연과 회차별 제출 지각·결제/환불·후기 기록도 표시한다.
- `/mypage/products/:id/sale-status`: 판매 중지·재개 화면. [판매 상태 관리](product-sale-status.md)를 따른다.
- `/mypage/products/new`, `/mypage/products/:id/edit`: 상품 등록·수정 화면. [상품 관리](product-management.md)를 따른다.
- `/mypage/seller-profile`, `/mypage/settlements`: 본인 판매자 프로필과 판매 수익 화면이다.
- `/mypage/profile`: `feature/profile-display-name`의 내 정보 화면. 이메일을 보여주고 표시 이름을 `PATCH /api/me`로 바꾼다. 비밀번호 변경 폼(`POST /api/me/password`, #84)도 이 화면에 있다. 저장 직전 계정을 다시 확인하며 비로그인은 로그인 후 이 화면으로 돌아온다. [상세](auth-login.md#내-정보-화면-2026-11-04-featureprofile-display-name)
- `/admin/products`, `/admin/products/:id`: 현재 소스에 포함된 관리자 상품 운영 화면. 권한은 서버가 판단하며 401은 로그인 안내, 403은 접근 권한 없음으로 표시한다. [상세](admin-product-moderation.md#관리자-화면-2026-11-04-featureadmin-product-ui)
- `/mypage/wallet/topup` 및 하위 결과 경로: 테스트 충전 화면. preview 경로는 명시적인 예시이며 지급 근거가 아니다.

문서 대조 기준 이력: 11월 4일 `3178e2e`(PR #67 포함), 문서 통합 `384546a`, 11월 5일 V3/V4 `c24f37d`를 거쳐 이번 기준은 `1e10d78`이다. V3/V4 당시 전체 백엔드 651건 통과와 V5/V6·정책 경계의 최초 실패 후 선택 재검증은 별도 기록이다. 최신 main 전체를 이번에 일괄 검증했다고 표현하지 않는다([검사 한계](team-progress.md#남은-검증-한계)).

문서 브랜치에 main `53bc38b`를 반영하고 프런트 전체 106건·lint·build가 통과했다. 직접 취소 사유 검증 보완과 문서 변경의 조합을 확인한 결과다. 사용자 브라우저 수동 확인·백엔드 전체 검사·원격 CI를 이번 실행으로 대체하지 않는다.

사용자는 실제 화면에서 상품 등록→주문→수락→결제→납품→구매 확정→정산, 취소·환불·잔액 반환을 확인했다. 결제창 취소·세션 만료·완료 화면 새로고침·결과 재확인도 이미 확인한 항목이다. [사용자 수동 검증 현황](manual-trade-verification.md)에 완료·남은 항목과 증거 범위를 정리한다.

아래는 문서에 보존된 이전 실행 결과다. 이번 문서 정리에서 재실행하지 않았다.

`refactor/project-conventions` 로컬 작업에서는 프런트 조회 훅·회원 확인 API·계정 캐시 제거 정책을 분리하고, 정산 백엔드의 service·dto 패키지를 정리했다. 프런트·백엔드 공통 가이드는 실제 구현 기준으로 교체했다. 격리 MySQL 8.4 전체 clean build 585건(실패·오류·건너뜀 0), 프런트 79건·lint·build가 통과했다. 실제 브라우저 수동 검증·원격 CI·PR·병합은 이번 로컬 검증과 별도다.

컨벤션 정리 브랜치에 main `37ee5a5`(관리자 화면 포함)를 반영한 뒤 프런트 테스트 93건·lint·build가 통과했다. 정산·회원 확인·계정 캐시 구조 정리와 관리자 화면의 조합을 로컬 자동 검사로 확인한 결과다. 기존 백엔드 585건 기록은 구조 정리 당시 실행 범위이며 이번 프런트 재검사와 구분한다.

과거 커밋별 검사 수와 실행 범위는 [검증 이력](verification-history.md)에 보존한다. 최신 작업의 테스트 결과는 해당 PR과 CI에서 확인하며 과거 검사 수를 합산하지 않는다.
