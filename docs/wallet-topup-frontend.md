# React 토스 테스트 충전 화면

작성일: 2026-11-02. 담당: 황준범. 브랜치: `feature/wallet-topup-api`.

## 1. 구현 범위

기존 흑백 AppLayout·마이페이지·공통 apiRequest를 재사용해 충전 금액 선택, 토스 주문서형 SDK 초기화, 결제 요청, 복귀 후 서버 승인·조회, 결과 재확인 화면을 구현했다. SDK는 `@tosspayments/tosspayments-sdk@2.10.0`으로 고정한다.

실제 테스트 결제는 아직 하지 않았다. 사용자 안내로 개인 `LancerPickFrontend/keys.env`를 확인했고, Vite에서 클라이언트 키 항목을 명시적으로 읽도록 연결했다. 기존 파일을 수정하거나 키 값을 출력하지 않았다. 테스트키로 결제 수단·약관 UI의 실제 로딩까지 확인했으며, 약관 동의·결제 실행·서버 승인은 하지 않았다. 실제 회원 인증·가입 연결도 별도다.

## 2. 경로와 확인

| 경로 | 동작 |
| --- | --- |
| /mypage/wallet/topup | 본인 지갑 접근 확인 후 금액·결제 수단 선택 |
| /mypage/wallet/topup/preview | API·SDK를 호출하지 않는 명시적 예시 화면 |
| /mypage/wallet/topup/{id}/success | 복귀 정보·서버 소유권/조건 확인 후 승인·상태 조회 |
| /mypage/wallet/topup/{id}/fail | 제공자 오류 문구를 노출하지 않고 서버 상태 확인 |
| /mypage/wallet/topup/{id}/status | DB 상태 조회, 필요한 경우 사용자 클릭으로 재확인 POST |

```powershell
cd C:\project\LancerPickFrontend
npm ci
npm run dev
```

미리보기: http://localhost:5173/mypage/wallet/topup/preview. 백엔드·DB·키가 없어도 화면을 볼 수 있다. 일반 경로는 본인 지갑 API가 필요하다. 정상 로그인·지갑이 없는 상황에서 고정 회원 ID나 예시 잔액으로 우회하지 않는다.

마이페이지의 실제 잔액 카드에는 충전 화면 링크, 예시 잔액 카드에는 충전 미리보기 링크를 둔다. 로그인 메뉴·표시 이름 등 전역 인증 UI는 인증 담당자가 연결한다.

## 3. 실제 연동 전 설정

현재 프런트 개인 설정 파일은 `keys.env`다. 없는 팀원은 `.env.example`을 복사해 `keys.env`를 만들며 기존 개인 파일은 덮어쓰지 않는다.

```dotenv
VITE_TOSS_CLIENT_KEY=CHANGE_ME
```

위 값을 본인의 **test_gck** 클라이언트 키로 교체하고 Vite를 재시작한다. Vite 기본 로더는 keys.env를 자동으로 읽지 않으므로 vite.config.ts에서 Node 내장 parseEnv로 읽어 VITE_TOSS_CLIENT_KEY 하나만 브라우저에 연결한다. 적용 우선순위는 셸 변수 → keys.env → 표준 .env 계열이며 빈 셸 값은 SDK를 끈다. 파일 전체·다른 VITE 변수·서버 시크릿을 define이나 process.env에 일괄 주입하지 않는다.

SDK와 Vite 설정은 테스트 gck만 허용하며 시크릿·라이브·개별 연동 ck 키는 거부한다. 클라이언트 키는 브라우저에 포함되는 공개 설정이다. gsk는 프런트에 넣지 않는다. keys.env는 Git에서 제외하고 Vite 기본 민감 파일 차단을 유지하면서 해당 원본 파일도 HTTP 제공을 차단한다. 파일을 public 폴더에 두지 않는다.

백엔드는 기존 [키 설정 안내](toss-test-payment-setup.md)에 따라 같은 세트의 테스트 시크릿과 `TOSS_TOPUP_ENABLED=true`를 설정한다. 기본 비활성화에서는 승인 API가 503을 반환하며 READY를 유지한다. 실제 Spring Security 인증 principal과 회원가입 지갑 생성도 연결돼 있어야 한다.

## 4. 화면·SDK 흐름

1. 금액 1~100만원을 정수로 검증한다. 소수·지수 표기·음수·0·범위 초과를 막는다.
2. 사용자가 결제 수단 선택을 누르면 SDK를 동적 로드하고 금액·결제 UI·약관 UI를 렌더한다. 화면 진입만으로 SDK를 호출하지 않는다.
3. PG 저장형 고객 기능은 사용하지 않고 ANONYMOUS로 초기화한다. 이는 PG의 고객 기능 설정이며 사이트 본인 인증·충전 소유권은 서버가 별도로 검사한다. 이메일·전화번호·회원 ID를 PG 고객 키로 보내지 않는다.
4. 현재는 선택한 결제 경로가 CARD일 때만 진행한다. 카드로 처리되는 간편결제도 여기에 포함된다. 가상계좌·입금 대기·외화·브랜드페이 등의 정상 지원은 별도다. 상점 UI에 다른 수단이 보일 수 있지만 이번 화면에서는 요청을 막는다.
5. 필수 약관 동의 후 결제 버튼을 누르면 서버에 신청을 저장한다. 주문번호·금액은 서버 응답을 사용한다. 기존 세션의 READY 신청이 있으면 조회·조건 확인 후 같은 신청으로 이어간다.
6. 금액과 신청 ID·주문번호·무작위 nonce·작성 시각만 sessionStorage에 기록한다. 복귀 마커 TTL은 30분이며 토스 결제 인증의 유효 시간과는 별개다. 토큰·paymentKey·시크릿은 이 저장소에 쓰지 않는다.
7. successUrl/failUrl은 같은 origin의 고정 경로에 nonce를 붙인다. windowTarget=self로 이동하며 화면에는 테스트 전용임을 명시한다.

필수 약관 상태·로딩·중복 클릭을 관리하고 SDK 객체는 화면 종료 시 정리한다. 결제 요청 이후 오류가 나면 새 신청을 자동 생성하지 않고 기존 신청 상태로 안내한다. 신청 POST 자체의 멱등 요청 키는 기존 계약대로 아직 없다.

## 5. 복귀·결과 처리

- success라는 경로 또는 HTTP 200만으로 완료를 표시하지 않는다. 서버 status=COMPLETED에서만 충전 완료다.
- 복귀 시 원래 세션 마커의 id·nonce·주문번호·금액과 URL 정보를 비교하고, 본인 조회 API 결과와도 다시 비교한다. 마커 없음·중복 파라미터·불일치 시 자동 승인하지 않는다. 최종 검증은 서버 승인 API가 담당한다.
- 승인 POST는 메모리 Promise로 1회만 실행한다. StrictMode·재렌더링·실패 때문에 자동 재전송하지 않는다. 항상 본인 GET 조회 후 호출하고, 승인 응답을 별도 계정 캐시로 재사용하지 않는다.
- PROCESSING/UNKNOWN은 확인 중으로 표시하고 사용자 클릭으로 reconcile을 호출한다. 페이지 새로고침 자체는 승인 POST를 반복하지 않는다. 자동 외부 재승인·새 충전 재시도·주기 재확인은 없다.
- paymentKey·nonce·제공자 오류 쿼리는 캡처 후 replace 탐색으로 주소에서 제거한다. no-referrer 메타도 적용했다. raw 제공자 오류 문구는 표시하지 않는다.
- 완료 시 지갑 쿼리를 무효화하고 세션 마커를 정리한다. 로그아웃·계정 변경 시 clearWalletCache가 지갑 쿼리를 취소/제거하고 복귀 마커·승인 메모리도 정리한다. 실제 인증 흐름에서 이 함수를 호출하는 연결은 남아 있다.
- 세션 만료·창 닫기·저장소 차단·잘못된 복귀는 자동 결제를 우회하지 않고 상태 조회/로그인 안내로 처리한다. GET도 인증이 필요하다. 전체 서버 상태가 항상 자동 복구된다는 의미는 아니다.

## 6. 검증 결과·남은 범위

- 프런트 lint·build(타입 검사 포함)·test:api 15건 통과. 금액/큰 ID, nonce/조건/중복 파라미터, 테스트 키 종류, 저장 필드 제한, 승인 1회·실패 무재시도·로그아웃 정리를 검사했다.
- 별도 임시 localhost 응답 서버와 Vite로 예시 화면을 확인했다. 실제 회원·DB·토스 호출과 구분한다. 소수 입력 차단·3만원 선택·예시 결제 버튼 비활성화·390/320px 가로 넘침 없음, UNKNOWN→사용자 재확인→COMPLETED, FAILED 표시, 위조 success URL 무승인·쿼리 제거를 확인했다. 응답 대역의 승인 호출 0회·재확인 1회, 브라우저 오류/경고 없음도 확인했다.
- 키를 비운 일반 화면은 결제 수단 버튼을 비활성화하고 SDK 스크립트를 로드하지 않았다. 이후 keys.env 연결로 별도 검사 서버에서 실제 SDK의 결제 수단 iframe·약관 iframe이 각각 1개, 앱 오류/로딩 메시지 없음까지 확인했다. 키·iframe URL을 출력하지 않았고 결제·약관 동의·승인·재확인 요청은 하지 않았다. 인증은 임시 localhost 응답을 사용했으므로 실제 로그인 검증은 아니다.
- HTTP HEAD로 /keys.env와 @fs 절대 경로가 403으로 차단됨을 확인했다. 원문을 가져오는 GET은 사용하지 않았다. 앞서 임의로 만든 미변경 .env.local 자리 표시자 복사본만 예시 파일과 동일한지 비교 후 제거했고, 기존 keys.env는 보존했다.
- SDK 설치 시 전체 의존성 감사는 moderate 12건을 보고했고, `npm audit --omit=dev --json`에서는 배포 의존성 취약점 0건이었다. 개발 도구 항목은 별도 검토하며 강제 버전 변경을 하지 않았다. SDK는 1개 패키지만 추가됐고 기존 라이브러리 버전은 유지했다.
- 실제 카드 테스트·필수 약관 이벤트·모바일 복귀·인증/CSRF 만료·실제 DB 잔액 반영·서버 재시작 복구를 인증 담당자와 함께 검증해야 한다. SDK UI 로딩만 확인한 결과를 결제 성공으로 표현하지 않는다. 이번 단계에서 백엔드 전체 테스트를 새로 실행한 것은 아니며 기존 서버 검증 기록은 [승인 문서](wallet-topup-approval.md)를 따른다.

SDK 근거: [공식 SDK 초기화](https://docs.tosspayments.com/sdk/v2/js/environment), [주문서형 SDK](https://docs.tosspayments.com/sdk/v2/js/payment-widget).

## 2026-11-03 사용자 테스트·초기 약관 상태 보완

사용자가 가입·로그인 API로 브라우저 세션을 만든 뒤 토스 테스트 결제를 진행했다. 서버 충전 비활성화 오류를 확인하고 활성화 설정 후 성공했으며, 제공한 화면에서 가입 100만원·충전 5만원·잔액 105만원·내역 2건을 확인했다. 이는 사용자 실행 결과이며 에이전트의 브라우저 재현·DB 원문 검사 또는 새로고침 중복 지급 검사 완료를 뜻하지 않는다.

추가로 최초 진입 시 약관은 체크되어 있지만 결제 버튼이 비활성화되는 증상을 보고했다. 기존 React 상태는 false로 시작해 agreementStatusChange가 와야만 true가 되었다. V2 웹 SDK 공개 API에는 초기 약관 상태 조회 메서드가 없으므로 초기 상태를 미확인(null)으로 구분한다. 위젯 준비 완료 뒤 요청을 허용하고 실제 필수 약관 검증은 SDK requestPayment에 맡긴다. 변경 이벤트에서 명시적 미동의를 받으면 버튼과 요청을 막고, 재동의 시 화면 오류를 정리한다. 미확인을 동의 완료로 기록하거나 실제 약관 체크를 강제하지 않는다.

수정 브랜치: `fix/wallet-checkout-agreement`. 프런트 lint·타입 검사 포함 build·기존 API/세션 테스트 21건 통과. 해당 21건은 SDK iframe의 초기 체크 상태를 재현하는 UI 검사가 아니다. 사용자 브라우저에서 초기 체크 시 결제 버튼 활성화, 해제 시 비활성화, 재체크 시 활성화를 추가 확인해야 한다. 백엔드 코드·설정은 이번 수정에서 변경하지 않았다.

같은 사용자 테스트에서 결제 수단 단계 진입 후 금액을 다시 고를 수 없는 문제를 추가 확인했다. 신청 생성 전에는 `충전 금액 변경` 버튼으로 금액 단계에 돌아가 입력/프리셋을 다시 선택할 수 있게 했다. 기존 위젯 제거를 기다린 뒤 단계를 바꾸고, 다음 결제 수단 진입 시 새 금액으로 다시 렌더링한다. 로딩 중에는 복귀·결제를 막고, 이미 만든 신청 또는 저장된 이어가기 신청은 금액을 바꾸지 않으며 상태 확인 링크를 사용한다. 제거 실패 시 새 위젯을 겹쳐 만들지 않고 오류와 재시도를 제공한다. 과거 위젯의 지연 이벤트는 현재 위젯 상태를 변경하지 않는다. 이 단계 복귀 동작은 브라우저 추가 확인 대상이다.
