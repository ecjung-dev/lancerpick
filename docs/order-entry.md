# 상품 상세에서 주문 진입

## S5 신규 계약 최소 금액 안내

공개 상품 상세의 `minimumOrderAmount`는 서버가 신규 주문에 적용하는 계약 최소 금액이다. 계약 주문(V2 호환 또는 V3)에서는 10,000원, 기존 주문 정책(LEGACY_V1)에서는 `null`을 반환한다.

- 계약 최소 금액 미만 상품은 상세에서 주문 진입 링크 대신 안내를 표시한다. 주문 작성 주소로 직접 접속해도 신규 요청을 보낼 수 없다.
- 서버는 주문 생성 시 최신 상품 가격을 다시 검증하고 미달이면 409 `CONTRACT_MINIMUM_AMOUNT_NOT_MET`을 반환한다. 이미 생성된 주문의 같은 요청 키 재확인은 그대로 처리한다.
- 상품 등록·수정 가격 범위와 신규 계약 활성화 설정 기본값은 유지한다.
- main `2272969` 기준 격리 MySQL의 주문 생성·상품 조회·공개 API 테스트 71건과 프런트 자동 테스트 204건·빌드·린트를 통과했다. 실제 브라우저 조작과 원격 CI는 별도다.

> 최신 수동 확인(2026-11-04): 사용자가 실제 화면의 일반 거래 완료·정산, 취소·환불·잔액 반환과 기본 충전 실패 흐름 확인을 완료했다. 아래 날짜별 미확인·후속 표기는 당시 기록이며, 현재 남은 확인과 보류 사항은 [사용자 수동 검증 현황](manual-trade-verification.md)을 따른다.

> 문서 읽기 기준(2026-11-04): 아래 날짜·브랜치별 구현 및 검증 설명은 당시 기록이다. 현재 반영 여부·남은 작업은 [현황표](current-status.md), 실행 설정은 [루트 README](../README.md), API 계약은 [API 명세](api-spec.md)를 따른다. 과거의 미구현·병합 전 표현과 검사 수를 현재 상태로 확대하지 않는다.

## 2026-11-04 병합 후 실제 화면 확인 당시 기록

## 구현

- 상품 상세 → /products/:id/order → 요구사항 작성 → 기존 POST /api/orders → 주문 상세 이동.
- /api/me·상품을 재조회한다. 비로그인·자기 상품의 작성 폼을 차단하고 제출 직전 계정을 다시 검사한다. 최종 권한·상품 상태·가격·버전은 서버가 판단한다.
- 기존 createOrder와 CSRF 클라이언트 사용. 상품 ID·조회 버전·정규화한 요구사항·UUID만 전송하며 가격·구매자·판매자 ID를 본문에 보내지 않는다.
- 요구사항 1~5000 코드 포인트 검사. 전송 중 버튼과 ref로 중복 클릭 방지, 자동 재시도 없음.
- 계정·상품별 sessionStorage에 전송 직전 본문·키 저장. 저장 불가·손상 시 신규 전송 차단. 성공 후 제거한다. 불확실한 결과는 입력을 잠그고 같은 요청 재확인·주문 목록 확인을 제공한다. 새로고침 후에도 같은 본문·키를 복원한다.
- 400/401/403/404/409는 제출 중단·상품/주문 목록 재확인. 버전 충돌을 자동 덮어쓰지 않는다.
- 요구사항은 현재 탭에 남을 수 있으나 인증 토큰·비밀번호를 저장하지 않는다. 운영 로그인/로그아웃 공통 저장값 정리, 여러 탭/새 창과 탭 종료 후 결과 확인은 후속이다.
