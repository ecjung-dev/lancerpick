## 2. C·D 호출 경계 제안

현재 확정 원칙은 업무 시작 서비스의 단일 트랜잭션과 주문 → 구매자 지갑 잠금 순서다. 아래는 이를 구체화하는 제안이며 클래스 이름이나 구현 완료를 뜻하지 않는다.

| 업무 | 시작점 제안 | 같은 트랜잭션 안의 책임 |
| --- | --- | --- |
| 최초 결제 | 주문 결제 조정 서비스(C·D 공동 검토) | 주문 잠금·자격 검증 → D의 지갑·결제 처리 → C의 진행 상태·납기·확인 시각·이력 |
| 유료 취소·승인 | 주문 취소 서비스(C) | 주문 잠금·당사자·취소 자격 검증 → D의 환불 → C의 주문 취소·대기 요청 종료·이력 |
| 구매 확정 | 주문 완료 서비스(C) | 주문 잠금·검수 대기·취소 요청 검사 → D의 정산 생성 → C의 완료·이력 |

D의 내부 금액 처리는 같은 트랜잭션에 참여한다. C→D 호출 중 D가 다시 C의 업무 시작 서비스를 호출하는 순환을 만들지 않는 방향으로 검토한다. 금액 처리 실패를 숨기지 않고 전체를 롤백한다. 잠금 담당 서비스, 내부 메서드 입력·반환값, 재호출 결과까지 합의한 뒤 구현한다.
