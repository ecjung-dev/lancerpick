# 방 전환 후 미확정 채팅 전송 키 보존

2026-11-09, 황준범. `fix/chat-pending-message`, main `44c7857`(#142) 기준. 회원 정책 `feature/member-change-policy`·주문 표시 PR #144와 별도다.

## 문제와 수정

`ChatDock`은 방을 바꾸거나 닫으면 기존 `ChatConversation`을 해제한다. 기존 전송 중복 방지 키는 그 컴포넌트의 ref에만 있어, 서버가 저장했지만 응답을 확인하지 못한 상태에서 다른 방을 열면 사라졌다. 같은 본문을 새 UUID로 보내면 기존 서버 UNIQUE 제약으로는 별개의 메시지이므로 중복 저장될 수 있다.

미확정 명령의 UUID·본문·전송 상태를 계정/주문별 QueryClient 메모리 캐시로 옮겼다. 일반 미전송 입력은 계속 컴포넌트 상태이며 방 전환/닫기 시 지운다. 미확정 명령만 방/전체 창을 닫아도 남겨 다시 열면 복원한다. 소켓/REST 전송 자체는 기존 경로를 재사용하고 임의의 자동 재전송을 추가하지 않는다.

| 상황 | 동작 |
| --- | --- |
| 전송 시작 | UUID·정리된 본문을 먼저 보관, 같은 명령의 동시 중복 클릭 차단 |
| 방 전환/창 닫기 | 컴포넌트를 해제해도 미확정 명령 유지. 다시 열면 본문과 진행 상태 복원 |
| 응답 불명확 | 편집을 막고 같은 본문·UUID로 재시도. 미확정 키를 GC 시간으로 자동 폐기하지 않음 |
| 성공 응답/본인 저장 이력 확인 | 해당 UUID만 정리. 해제된 컴포넌트의 성공 응답도 같은 계정이면 현재 방 조회를 갱신 |
| 최초 요청의 확정 거절 | 명령을 정리하고 같은 화면에서는 입력을 복원해 수정 허용 |
| 재시도의 거절 | 최초 요청의 성공 여부를 입증하지 못하므로 UUID를 보존. 재시도 제한 등으로 새 키가 생기지 않음 |
| 늦은 실패 | 재시도 회차를 비교해 더 최근 전송 상태를 덮어쓰지 않음. 오래된 성공도 다른 UUID는 지우지 않음 |
| 로그아웃·계정 전환 | 공통 개인 캐시 정리가 미확정 본문/UUID도 제거. 이전 계정의 늦은 응답은 세대 검사로 무시 |

메모리 전용이며 localStorage·sessionStorage·DB는 추가하지 않았다. 브라우저 새로고침/종료 후까지 UUID를 복구하거나 다른 기기와 동기화하는 기능은 제공하지 않는다. 계정 경계와 서버의 회원·당사자·상태·UNIQUE 검증은 유지한다.

## 구현 위치

- `pending.ts`: 회원/주문별 캐시 키, 명령 시작·확정/불명확·재시도 회차·계정 검사.
- `queries.ts`: `skipToken`을 사용한 데이터 전용 관찰. 캐시 무효화가 재전송이나 원천 초기화를 유발하지 않는다.
- `OrderChatPanel`: 일반 입력과 미확정 명령 분리, 해제 후 응답 처리, 저장 이력과 UUID/작성자 대조, 기존 전송 경로 재사용.

## 검증

프런트 typecheck·lint·전체 `test:api` **280건**·build 통과. 신규 회귀 6건은 방 관찰 해제/GC와 UUID 보존, 다른 주문 분리, 재시도 본문 고정, 늦은 실패/성공, 이력 확인, 최초 거절과 재시도 거절의 차이, 캐시 무효화 무전송, 로그아웃/같은 계정 재로그인 후 늦은 응답 차단을 포함한다. 기존 번들 500kB 초과 경고는 남아 있다.

Edge 격리 브라우저/API 응답 대역에서 POST 응답을 보류한 상태로 (1) 다른 방 이동 후 복귀, (2) 전체 창 닫기 후 재열기를 수행했다. 서버 저장 후 503을 돌려준 뒤 재시도해 두 경우 모두 같은 UUID/본문으로 POST 2회·저장 1건을 확인했다. (3) 기존 컴포넌트 해제 후 늦은 성공 응답도 다시 연 방에 반영되고 추가 POST 없이 저장 1건이었다. 합계 POST 5회·새 저장 메시지 3건이다. 실제 토큰/회원/개인 DB는 사용하지 않았다.

기존 브라우저 회귀도 목록·최소화·REST 전송·종료 거래 조회 전용·검색·경로 유지·알림 패널·320/390/768px·로그아웃/계정 전환·401 정리를 통과했다. 실제 서버 STOMP 방 전환과 원격 CI는 이 변경에서 확인하지 않았다. 서버·DB 변경이 없어 백엔드를 이 브랜치에서 재실행하지 않았으며 회원 정책 브랜치 검사 결과와 합산하지 않는다.

후속 main 통합(같은 날): `60b7b7f`(#143 판정 기록·#144 수락 버튼·#145 B4 발견 보완)를 반영했다. 코드 충돌은 없었고 현황·작업표 두 문서의 기록을 양쪽 보존했다. 통합 후 백엔드 `compileTestJava`, 프런트 280건·build 통과. 전체 백엔드 테스트·실서버·브라우저를 이 통합 직후 다시 실행한 결과는 아니다. 별도 회원 정책 브랜치의 보존된 커밋에는 영향을 주지 않았다.
