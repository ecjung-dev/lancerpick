각자 자기 기능의 화면·서버·합의된 DB 매핑·검증·문서를 책임진다. 주담당은 완료 책임이며 공동 구현·지원이 가능하다. 조율·공통 개발·리뷰 시간도 작업량에 포함한다. 기본 교차 검토는 김창재↔박소현, 정은찬↔황준범의 출발안이며 거래·금액은 정은찬·황준범 공동 검토다. 별도 React 공동 담당·검토자 상세·배포 담당은 원본의 별도 확정 항목으로 남긴다.

## 책임 경계와 배정 이력

신규 테이블·컬럼·제약·인덱스·Flyway 설계/변경은 황준범 담당이다. 각 기능 담당은 데이터 요구를 협의하고 합의된 스키마에 맞춰 구현한다. 마이그레이션 전 엔티티만 main에 올리거나 기능 브랜치에서 독자 DDL을 추가하지 않는다.

공통 스케줄러·Batch·저장소·계측은 정은찬·황준범이 나눈다. Redis는 이번 발표 범위 제외이며 재개 시 두 사람이 공동 담당한다. 채팅·Batch·문서 저장소를 황준범에게 동시에 착수시키지 않는 순서를 보존한다.

김창재의 기존 회원/인증·관리자 책임과 후속 합의로 황준범에게 배정된 신규 회원 목록·제재는 구분한다. 과거 2·3인 역할 제안과 내부 알림 담당 정정은 [변경 이력](change-history.md#conflicts)에 보존한다. 항목별 선행·상태는 [진행 현황](project-progress.md)에서 관리한다.

본 문서는 공통 개발 규칙 11장 ‘협업과 검토’를 구체화한다. 기존 개발 규칙의 기능별 책임, API·DB 변경 관리, 검증 및 보안 원칙을 유지한다.

확정 운영 정책: PR 작성자 외 최소 1명 승인, Squash merge, main 직접 Push 금지, 필수 CI 실패 시 병합 금지.

브랜치 명명 방식, Commit 메시지 형식, 기본 리뷰 담당자 배정 등은 팀의 추가 합의가 필요한 제안 사항으로 구분한다.

### 1. 기본 협업 원칙

모든 팀원은 동일한 GitHub 저장소에서 작업한다.

main은 검증된 코드를 통합하는 기본 브랜치로 사용한다.

기능 개발, 오류 수정, 설정 변경은 별도 작업 브랜치에서 진행한다.

main에 직접 Push하지 않으며 모든 변경은 Pull Request(PR)를 통해 병합한다.

API·DB·공통 코드 변경은 영향을 받는 담당자에게 공유한다.

기능을 지나치게 크게 묶지 않고 검증 가능한 작은 단위로 통합한다.

기능 담당자는 해당 기능의 화면·API·DB 변경·검증에 대한 완료 책임을 가진다.

공동 구현과 지원은 가능하며 실제 기여 범위를 PR 또는 작업 기록에 남긴다.

다른 팀원의 변경 사항을 임의로 덮어쓰거나 작업 이력을 무단 변경하지 않는다.

main 최신화 → 작업 브랜치 → Commit → Push → PR → CI·코드 리뷰 → Squash merge → main

main은 항상 빌드 가능한 상태를 유지하는 것을 원칙으로 한다.

완료되지 않은 기능은 Draft PR에서 검토할 수 있지만, 검증되지 않은 상태로 main에 병합하지 않는다.

### 2. 브랜치 전략

다음 브랜치 명명 규칙을 제안한다.

| 브랜치 | 용도 | 예시 |
| --- | --- | --- |
| main | 통합 브랜치 | main |
| feature/* | 신규 기능 개발 | feature/product-list |
| fix/* | 오류 수정 | fix/login-error |
| refactor/* | 동작 변경 없는 구조 개선 | refactor/order-service |
| test/* | 테스트 추가·개선 | test/payment-service |
| docs/* | 문서 변경 | docs/api-guide |
| chore/* | 개발 환경·설정 변경 | chore/gradle-config |
| ci/* | CI 설정 변경 | ci/github-actions |

브랜치 이름은 영문 소문자, 숫자, 하이픈을 기본으로 사용하며 종류와 작업 이름을 /로 구분한다.

위 명명 규칙의 의무 적용 여부는 팀 합의 후 확정한다.

초기 MVP 단계에서는 별도의 develop 브랜치를 운영하지 않는 것을 권장한다. 필요성이 확인되면 팀 합의 후 변경한다.

작업 시작 전 변경 사항을 확인한다.

```
git status
```

미완료 변경이 없는 상태에서 main을 최신화한다.

```
git switch main
git pull --ff-only origin main
```

새 작업 브랜치를 생성한다.

```
git switch -c feature/product-list
```

이미 생성한 브랜치가 있다면 새로 만들지 않고 이동한다.

```
git switch feature/product-list
```

하나의 브랜치는 하나의 명확한 작업 목표를 가진다.

기본적으로 작업 목적별 브랜치를 생성한다.

두 명 이상이 같은 기능을 공동 개발할 때는 담당 범위와 작업 파일을 먼저 협의한다.

공유 브랜치를 사용하는 경우 다른 팀원이 Push한 이력을 임의로 Rebase하거나 강제 Push하지 않는다.

서로 다른 브랜치에서 작업한 내용을 통합할 때는 변경 범위와 충돌 가능성을 확인한다.

### 3. 작업 시작 및 종료 절차

IntelliJ에서 현재 브랜치를 확인한다.

```
git status로 미완료 변경 사항을 확인한다.
```

기존 작업이 있다면 Commit하거나 안전하게 임시 보관한다.

새 작업이라면 최신 main을 기준으로 브랜치를 생성한다.

기존 작업을 계속한다면 해당 작업 브랜치로 이동한다.

담당 기능과 관련된 API·DB·공통 코드 변경 사항을 확인한다.

기능을 구현한 뒤 관련 테스트를 실행한다.

작업 목적이 구분되는 시점마다 Commit한다.

임시 디버깅 코드와 불필요한 생성 파일을 Commit하지 않는다.

비밀번호·토큰·실제 환경변수 파일을 Commit하지 않는다.

공통 파일을 변경해야 한다면 관련 담당자에게 공유한다.

다른 담당자의 코드를 수정할 때는 변경 목적과 영향 범위를 확인한다.

작업 브랜치가 오래 유지되는 경우 main의 최신 변경 사항을 확인한다.

변경 파일과 Diff를 검토한다.

관련 빌드와 테스트를 실행한다.

변경 사항을 Commit한다.

작업 브랜치를 GitHub에 Push한다.

PR을 생성하거나 기존 PR을 업데이트한다.

미완료 사항과 알려진 제한을 기록한다.

작업이 하루 안에 완료되지 않아도 브랜치를 유지할 수 있다.

미완성 코드를 공유해야 할 경우 Draft PR을 사용하며, 완료 조건을 충족하기 전에는 병합하지 않는다.

### 4. Commit 규칙

다음 형식을 기본 규칙으로 제안한다.

```
type: 변경 내용
```

| Type | 사용 목적 | 예시 |
| --- | --- | --- |
| feat | 기능 추가 | feat: 상품 목록 조회 구현 |
| fix | 오류 수정 | fix: 로그인 오류 처리 수정 |
| refactor | 구조 개선 | refactor: 주문 검증 로직 분리 |
| test | 테스트 추가·수정 | test: 결제 중복 요청 테스트 추가 |
| docs | 문서 수정 | docs: API 명세 업데이트 |
| chore | 설정·환경 변경 | chore: Gradle 설정 정리 |
| ci | CI 설정 변경 | ci: GitHub Actions 검사 추가 |

Commit 메시지는 실제 변경 내용을 명확하게 설명한다.

Commit 형식의 의무 적용 여부는 팀 합의 후 확정한다.

서로 다른 목적의 변경은 가능한 한 별도 Commit으로 구분한다.

Commit 전에 변경 파일과 Diff를 확인한다.

.env, 비밀번호, 인증 토큰, API 키 등 비밀정보를 포함하지 않는다.

.env.example에는 실제 비밀값을 포함하지 않는다.

개인 IDE 설정, 캐시, 빌드 결과물은 .gitignore 정책에 따른다.

package-lock.json, Gradle Wrapper, Flyway 마이그레이션 파일 등 재현에 필요한 파일은 버전 관리한다.

다른 팀원의 변경 사항을 본인의 작업으로 잘못 기록하지 않는다.

Windows 기준 주요 작업은 다음과 같다.

Commit: Ctrl + K

Push: Ctrl + Shift + K

Pull: Git → Pull

브랜치 전환: 브랜치 선택 메뉴

변경 사항 확인: Commit 또는 Git 도구 창

단축키는 IntelliJ Keymap 설정에 따라 다를 수 있다.

Commit은 로컬 Git 저장소에 변경 이력을 기록하는 작업이다.

GitHub에 변경 사항을 반영하려면 Push해야 한다.

### 5. Push 및 Pull 규칙

작업 브랜치를 처음 Push할 때:

```
git push -u origin feature/product-list
```

원격 추적 브랜치가 설정된 이후에는 다음 명령을 사용할 수 있다.

```
git push
```

Push 전 다음 사항을 확인한다.

현재 브랜치

Commit 대상과 변경 내용

비밀정보 포함 여부

다른 담당자에게 영향을 주는 변경 여부

main을 최신화할 때:

```
git switch main
git pull --ff-only origin main
```

--ff-only는 Fast-forward가 가능한 경우에만 업데이트하며, 자동 병합 커밋을 생성하지 않는다.

미완료 변경 사항이 있으면 먼저 Commit하거나 Stash로 안전하게 보관한다.

Stash를 사용한 경우 복원 시 충돌이 발생할 수 있으므로 복원 결과를 확인한다.

기존 작업 브랜치에 main의 최신 변경을 반영해야 할 경우:

```
git switch feature/product-list
git fetch origin
git merge origin/main
```

병합 후 변경 사항과 관련 테스트를 확인한다.

충돌이 발생하면 충돌 해결 절차를 따른다.

공유 중인 브랜치에서는 팀원 동의 없이 Rebase하거나 강제 Push하지 않는다.

Push가 거절되면 먼저 원인을 확인한다.

가능한 원인은 다음과 같다.

원격 브랜치에 새로운 Commit이 존재함

브랜치 보호 정책 위반

저장소 접근 권한 부족

인증 실패

문제를 해결하기 위해 무조건 git push --force를 실행하지 않는다.

### 6. Pull Request 규칙

작업이 검증 가능한 단위로 완료되면 PR을 생성한다.

조기 검토나 협업이 필요하면 Draft PR을 생성할 수 있다.

Draft PR은 검토용으로 사용하며 완료 전에는 병합하지 않는다.

모든 PR에는 다음 내용을 포함한다.

변경 목적

어떤 기능을 구현하거나 문제를 해결했는가?

영향 범위

API 계약이나 DB 구조가 변경되는가?

실행한 빌드와 테스트

정상·오류 동작 확인 결과

미완료 사항 또는 알려진 제한

관련 자료

해당하지 않는 항목은 해당 사항 없음으로 표시할 수 있다.

PR은 가능한 한 작은 기능 단위로 작성한다.

예를 들어 상품 관리 기능은 다음과 같이 구분할 수 있다.

상품 목록 조회

상품 상세 조회

상품 등록

상품 수정

단, 화면·API·DB가 함께 변경되어야 정상적으로 검증할 수 있는 기능은 하나의 PR에 포함할 수 있다.

PR을 작게 나누기 위해 동작하지 않는 중간 상태를 main에 병합하지 않는다.

### 7. 코드 리뷰 규칙

PR 작성자 외 최소 1명의 승인을 받아야 한다.

API·DB·공통 코드 변경 시 관련 담당자에게도 검토를 요청한다.

미해결 필수 수정 의견이 있는 PR은 병합하지 않는다.

수정 요청을 받으면 내용을 반영한 뒤 다시 검토를 요청한다.

PR 승인 이후 새로운 Commit이 추가되면 변경 내용을 검토자가 다시 확인한다.

GitHub에서 새 Commit에 대한 기존 승인 무효화 설정을 사용할 수 있는 경우 이를 활성화한다.

필수 승인 조건을 충족한 상태에서만 병합한다.

리뷰 및 공동 구현 기여를 작업 기록에 남긴다.

GitHub의 승인 무효화 설정 등 구체적인 강제 방식은 저장소에서 확인하고 문서와 일치하도록 구성한다.

### 8. CI 및 병합 조건

main 대상 PR에서 GitHub Actions CI를 실행한다.

필수 검사 범위는 공통 개발 규칙 12장 ‘테스트와 완료 기준’을 따른다.

기본 검증 범위는 다음과 같다.

프런트엔드 TypeScript 타입 검사

프런트엔드 빌드

백엔드 Gradle 빌드 및 관련 테스트

DB가 필요한 테스트의 격리된 MySQL 환경 및 Flyway 검증

PR 대상 브랜치에 이미 있는 Flyway 마이그레이션(`V*.sql`)의 수정·삭제·이름 변경 차단(`Migration immutability` job)

구체적인 CI 구축 방법, 환경변수, GitHub Actions 설정은 공통 개발 환경 구축 가이드에서 관리한다.

다음 조건을 모두 충족해야 병합할 수 있다.

작성자 외 최소 1명의 승인

필수 CI 검사 성공

미해결 필수 수정 의견 없음

관련 문서 및 DB 변경 파일 반영

알려진 제한과 미완료 사항 기록

필수 검사로 지정된 항목이 최신 PR 변경 사항을 검증했는지 확인한다.

PR 병합은 Squash merge를 사용한다.

Squash merge는 PR의 여러 Commit을 하나의 Commit으로 묶어 대상 브랜치에 반영하는 방식이다.

PR 병합 후 다음 작업은 최신 main에서 새 브랜치를 생성한다.

GitHub Ruleset 또는 브랜치 보호 설정을 통해 다음 정책을 강제한다.

main 직접 Push 제한

PR을 통한 병합

작성자 외 최소 1명 승인

강제 Push 및 브랜치 삭제 제한

브랜치 보호 규칙은 일반 팀원뿐 아니라 저장소 관리자에게도 적용하는 것을 원칙으로 한다.

규칙 우회 권한은 별도로 부여하지 않는다.

규칙을 문서에 작성하는 것과 GitHub에서 실제 강제하는 것은 구분한다.

저장소의 권한 및 요금제에 따라 설정 가능 여부를 확인하고, 실제 차단 동작을 검증한다.

### 9. Merge Conflict 해결

여러 팀원이 같은 파일의 겹치는 부분을 수정하거나 Git이 변경 사항을 자동으로 통합할 수 없을 때 충돌이 발생할 수 있다.

충돌이 발생한 파일을 확인한다.

IntelliJ Merge 도구에서 양쪽 변경을 비교한다.

각 변경의 목적을 확인한다.

필요한 코드를 보존하여 충돌을 해결한다.

충돌 표시와 누락된 변경 사항이 없는지 확인한다.

관련 빌드와 테스트를 다시 실행한다.

API·DB·공통 코드 충돌은 관련 담당자와 결과를 확인한다.

병합을 완료하고 필요한 경우 Commit한다.

Git 명령으로 병합을 시작했다면 충돌 해결 후 다음과 같이 진행할 수 있다.

```
git status
git add <해결한-파일>
git merge --continue
```

병합 방식이나 충돌 상태에 따라 필요한 명령이 달라질 수 있으므로 git status의 안내를 우선 확인한다.

React 라우팅 및 전역 설정

공통 API 요청 코드

Spring Security 설정

공통 오류 처리

Gradle 설정

Flyway 마이그레이션 파일

변경 전에 관련 담당자와 협의하여 충돌 가능성을 줄인다.

Flyway 마이그레이션 번호가 충돌하면 공유 환경 적용 여부를 먼저 확인한다.

이미 공유 환경에 적용된 파일은 수정하지 않고 새로운 마이그레이션 파일을 추가한다.

마이그레이션 변경은 기존 데이터 보존과 관련 기능에 대한 영향을 검토한다.

### 10. 긴급 오류 수정

main에 병합된 코드에서 오류가 발견되면 별도의 fix/* 브랜치를 생성한다.

```
git switch main
git pull --ff-only origin main
git switch -c fix/payment-error
```

오류를 수정하고 필요한 테스트를 추가한 뒤 PR을 생성한다.

긴급 수정도 다음 조건을 충족해야 한다.

관련 기능 검증

작성자 외 최소 1명 승인

미해결 필수 수정 의견 해결

긴급 상황이라는 이유로 CI 실패 상태의 병합을 허용하지 않는다.

별도의 예외 절차가 필요한 경우 기존 운영 정책을 임의로 우회하지 않고 팀 합의 및 문서 개정을 먼저 진행한다.

### 11. 작업 브랜치 정리

PR이 병합되면 로컬 main을 최신화한다.

```
git switch main
git pull --ff-only origin main
```

Squash merge는 작업 브랜치의 개별 Commit을 그대로 병합하지 않는다.

따라서 PR이 GitHub에서 정상 병합되었더라도 다음 명령이 실패할 수 있다.

```
git branch -d feature/product-list
```

이 경우 GitHub에서 PR이 병합되었는지, 필요한 변경 사항이 main에 반영되었는지, 브랜치에 보존할 추가 작업이 없는지 확인한다.

확인이 끝났다면 다음 명령으로 로컬 브랜치를 삭제할 수 있다.

```
git branch -D feature/product-list
```

-D는 Git의 병합 여부 검사를 생략하므로 반드시 확인 후 사용한다.

원격 작업 브랜치는 PR 병합과 작업 완료를 확인한 뒤 삭제한다.

GitHub의 PR 병합 후 브랜치 삭제 기능을 사용할 수 있다.

공동 작업 중인 브랜치는 다른 팀원의 작업 상태를 확인하기 전 삭제하지 않는다.

### 12. Git 사용 시 금지 사항

다음 행위를 금지한다.

main에 직접 Push

다른 팀원의 작업을 덮어쓰는 무단 강제 Push

비밀번호·토큰·API 키 등 비밀정보 Commit

필수 CI 검사 실패·미실행·대기 상태의 병합

필수 리뷰 승인 없이 병합

테스트 실패를 숨기기 위한 임의의 테스트 삭제·비활성화

공유 환경에 적용된 Flyway 마이그레이션 파일 수정

다른 사람의 코드를 본인 단독 작업으로 기록

충돌 원인을 확인하지 않은 일괄 덮어쓰기

원인을 확인하지 않은 git reset --hard 또는 브랜치 강제 삭제

비밀정보가 GitHub에 Push되었다면 다음 절차를 따른다.

팀에 즉시 공유한다.

노출된 비밀번호·토큰·키를 폐기하거나 재발급한다.

노출 범위와 관련 로그를 확인한다.

저장소에서 해당 정보가 다시 사용되지 않도록 수정한다.

필요하다면 Git 이력 정리 방법을 팀과 협의한다.

작업 시작
