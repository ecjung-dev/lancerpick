# 주문 생성 내부 서비스

작성일: 2026-11-02. 담당: 정은찬. 브랜치: `codex/order-create-service`.

## 구현 범위

API 명세 4·10·11절과 기존 SQL을 바탕으로 `OrderCreationService.create(buyerId, request)`를 구현했다. 주문·스냅샷·최초 이력을 실제 서비스 트랜잭션으로 저장한다. 반환값은 `Result(orderId, created)`이며 HTTP `OrderDetail` 응답이 아니다. Controller·인증·조회 DTO·React 연결은 아직 없다. `created=true`는 신규 생성, false는 동일 입력 재전송을 뜻하며 HTTP 연결 시 각각 201·200으로 변환해야 한다.

현재 main에 실제 회원·상품 Entity가 없어 해당 영역을 중복 구현하지 않았다. 주문 전용 `OrderCreationQueries`가 기존 members·products를 조회한다. 테스트 회원·상품은 SQL fixture이며 실제 가입·상품 등록 기능 완료를 의미하지 않는다.

## 처리 순서와 재전송

1. 인증 연결부에서 받은 구매자 ID와 요청 형식을 검증한다. 서비스 자체도 버전 누락·음수, ID·UUID·요구사항을 검사한다.
2. 구매자 회원 행을 잠근다. 회원이 없으면 AUTHENTICATION_REQUIRED로 거절한다. 이 검사는 실제 로그인 검증을 대신하지 않는다.
3. 구매자·정규화한 요청 키로 기존 주문과 스냅샷을 잠금 조회한다.
4. 기존 주문이면 상품 ID·최초 상품 버전·정규화한 요구사항을 비교한다. 같으면 기존 ID를 반환하고, 다르면 409 IDEMPOTENCY_KEY_REUSED로 거절한다.
5. 신규 요청이면 상품 행을 잠근다. 현재 가격·판매자·소요일·설명은 서버 조회값만 사용한다.
6. 상품 없음·관리자 숨김은 404 RESOURCE_NOT_FOUND, 판매 중지는 409 PRODUCT_NOT_ORDERABLE, 자기 상품은 409 SELF_PURCHASE_NOT_ALLOWED, 버전 불일치는 409 PRODUCT_VERSION_CONFLICT로 처리한다. 중복된 실패 조건에서는 이 검사 순서가 적용된다.
7. UTC Clock의 Instant를 마이크로초 LocalDateTime으로 변환한다. 주문 REQUESTED·스냅샷·최초 CREATED 이력을 같은 트랜잭션으로 저장한다.

성공했던 요청은 상품 수정·판매 중지·숨김이나 주문 종료 이후에도 기존 입력으로 재전송할 수 있다. 기존 키 확인은 현재 상품 조건 검사와 현재 거래 규칙 생성보다 먼저 수행한다. UUID는 소문자 하이픈 표준형, 요구사항은 공통 Unicode 공백·줄바꿈 정규화 결과로 비교한다. 새 키는 별도 주문을 생성한다. DB 오류 전부를 멱등 성공으로 바꾸거나 실패한 트랜잭션 안에서 재시도하지 않는다.

## 트랜잭션과 잠금 연결 기준

이번 구현은 주문 생성 진입점에만 READ_COMMITTED를 사용한다. REPEATABLE READ에서 없는 요청 키를 FOR UPDATE로 조회하면 다른 구매자의 신규 INSERT와 간격 잠금이 충돌할 수 있어 이를 피한다. 기본 DB 격리 수준·지갑 초기화의 기존 REPEATABLE READ 검증은 변경하지 않았다.

신규 주문의 잠금 순서는 **구매자 회원 → 요청 키 조회 → 상품**이다. 같은 구매자의 요청은 회원 행에서 직렬화하므로 다른 요청 키도 순서대로 처리한다. 같은 키 경쟁은 기존 저장 결과를 읽고 비교한다. 서로 다른 구매자는 상품 행에서 필요한 경우 직렬화된다. 처리량을 측정한 설계는 아니며 구매자 단위 직렬화의 비용은 남은 평가 항목이다.

서비스는 상위 READ_COMMITTED 트랜잭션에는 참여할 수 있으며 상위 롤백 시 세 기록도 함께 롤백한다. 격리 수준이 다르거나 지정되지 않은 기존 상위 트랜잭션에는 쓰기 전에 IllegalTransactionStateException으로 거절한다. REQUIRES_NEW로 상위 업무와 분리 커밋하지 않는다. Controller가 업무 시작 서비스로 호출하는 것이 기본 연결 방식이다.

이 순서는 이번 구현의 연결 기준이며 전원 합의나 회원·상품 담당자의 구현 완료를 뜻하지 않는다. 상품 수정·판매 상태·관리자 숨김 쓰기는 같은 products 행의 version을 일관되게 변경해야 한다. 다른 경로에서 상품 잠금 후 구매자 회원 잠금을 얻는 순서를 추가하기 전 담당자 간 검토가 필요하다. 결제·취소의 기존 **주문 → 구매자 지갑** 잠금 순서는 변경하지 않는다.

## 거래 규칙 원문

`OrderTerms.currentText()`는 [MVP 정책](mvp-spec.md)에서 주문 조건 보존·수락/결제·납기·수정 1회·취소/환불·구매 확정·수수료 규칙을 구성한 서버 원문 v1이다. 클라이언트가 termsSnapshot을 제출할 수 없다. 원문은 주문 생성 시 스냅샷에 복사하며 이후 서버 규칙이 바뀌어도 과거 원문을 다시 만들지 않는다.

현재는 내부 생성 경로만 구현했다. 구매자 화면에 규칙을 게시하거나 동의 UI·조건 확인 API를 연결한 상태가 아니다. 공개 API 연결 전에 원문과 화면 표시를 함께 리뷰해야 한다. 법적 효력을 보장하는 전자서명으로 표현하지 않는다.

## UTC 저장 보완

기존 Order·OrderHistory의 LocalDateTime/TIMESTAMP 매핑은 서울 JVM에서 DB 저장값이 9시간 어긋나도 JPA 재조회만으로 정상처럼 보이는 문제를 실제 재현했다. 주문·이력의 DATETIME 필드에 `@JdbcTypeCode(SqlTypes.LOCAL_DATE_TIME)`을 사용해 JDBC LocalDateTime으로 직접 전달하도록 보완했다. 서비스는 Clock의 시간대와 관계없이 Instant를 UTC로 변환한다. 기존 공통 JDBC UTC 설정이나 지갑 Entity는 변경하지 않았다.

검증은 JPA 재조회뿐 아니라 SQL DATE_FORMAT으로 orders·order_histories의 실제 저장 원문을 검사한다. 앞선 저장 테스트의 성공을 UTC 원문 검증 완료로 확대하지 않는다. 기존 업무 데이터에 대한 시간 보정 SQL은 실행하지 않았으며, 해당 데이터가 있다면 수정 전 원문·시각 출처를 별도로 점검해야 한다.
